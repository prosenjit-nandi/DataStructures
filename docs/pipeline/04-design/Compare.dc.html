Three stacks, one contract

All three implement datastructure.interfaces.Stack, so any of them can be dropped in for the others. What changes is what it costs you.

Pick this one when… You know the ceiling and can't afford a pause. Real-time paths, embedded, parsers with a bounded depth. You want it to just work and the workload is ordinary. This is the default choice. Elements are large or the depth is wildly unpredictable, and you'd rather pay per push than reserve up front.

Avoid ArrayStack when

The maximum depth is a guess. The current default of 10 000 is a magic number, and reserving for a worst case you invented is how you waste 40 MB on a stack that holds nine things.

Avoid ListStack when

A single resize pause would blow a latency budget. Amortized O(1) means one push in a thousand copies the whole array.

Avoid LinkedStack when

You're pushing millions of small elements. One node object per element costs more memory than the elements do, and the pointer-chasing defeats the cache.
In production you would use none of these — java.util.ArrayDeque is the JDK's stack and beats all three. These exist so you understand what it's doing.
